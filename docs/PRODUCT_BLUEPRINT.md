# SkyCast 产品全链路总纲

## 1. 产品定义

### 1.1 一句话定位

SkyCast 是面向风光、天文和强天气摄影用户的 AI 气象决策助手，融合雷达、卫星、地面气象、天文、地形与道路数据，给出可解释、可追溯、受安全约束的拍摄建议。

### 1.2 用户需要完成的任务（JTBD）

当用户考虑一次拍摄活动时，希望快速知道：

- 目标景观是否可能出现；
- 最佳时间、方向和地点；
- 是否值得付出出行成本；
- 天气变化会不会破坏计划；
- 当前位置和路线是否安全；
- 结束后能否复盘模型为什么正确或错误。

### 1.3 核心差异

普通天气产品以“天气信息”为终点；SkyCast 以“摄影决策”为终点。核心闭环是：

```text
发现机会 → 评估概率 → 选择地点 → 规划行程 → 动态提醒 → 安全退出 → 事件复盘 → 用户反馈 → 模型改进
```

## 2. 用户与场景

### 2.1 首要用户

1. 城市风光摄影师：关注朝霞、晚霞、云海和城市天际线。
2. 天文摄影爱好者：关注银河、月升月落、星轨、流星雨和云量。
3. 强天气摄影用户：关注雷暴景观，但需要明确风险边界。

### 2.2 首发场景

- 下班前判断当日晚霞是否值得拍；
- 出发前选择城市周边最佳拍摄点；
- 查看最近 1～3 小时雷达和卫星演变；
- 查看风暴未来 15/30/45/60 分钟概率范围；
- 通过历史时间轴复盘一次天气过程。

## 3. 端到端产品链路

| 链路 | 产品动作 | 工程产物 | 验收依据 |
|---|---|---|---|
| 用户研究 | 访谈、场景排序、痛点量化 | 访谈纪要、用户画像 | 至少 8 名目标用户、3 类场景 |
| 数据准入 | 核实来源、授权、频率、缺测 | 数据清单、数据契约 | 来源合法、时间字段完整 |
| 数据处理 | 质控、投影、时间对齐、缓存 | 标准化观测帧 | 可追溯、可重放、可降级 |
| 模型基线 | 规则模型、光流、持续性基线 | 离线评估报告 | 优于简单基线或标记实验性 |
| 决策引擎 | 场景评分、地点排序、安全过滤 | 可解释决策结果 | 原因、置信度、有效期完整 |
| 客户端 | 地图、时间轴、详情、提醒 | Android APK | 主路径可用、弱网可读 |
| 反馈闭环 | 拍到/未拍到、原因标注 | 标签与复盘记录 | 可用于后续校准模型 |
| 安全治理 | 官方/AI分层、过期和失败降级 | 审计日志、模型卡 | 不篡改官方预警，不误导 |
| 运营复盘 | 留存、使用漏斗、模型效果 | 指标看板 | 决策价值与模型质量分开统计 |

## 4. 功能架构

### P0：4 周面试版

- 城市首页：当前天气、日出日落、今日场景机会；
- 朝晚霞：评分、概率、染色窗口、方向、影响因素；
- 场景地图：热力格点和候选拍摄点；
- 雷达地图：历史动画、官方预警叠加；
- 短临研判：15～60 分钟回波概率锥；
- 时间轴追溯：一次完整历史过程重放；
- 数据说明：来源、时间、置信度、模型版本。

### P1：8 周作品版

- FY-4 云产品融合；
- 天文景观评估；
- 安全观测点和撤离路线；
- C++ 雷达渲染、地形地平线和空间计算；
- 通知订阅和重复提醒抑制；
- 用户结果反馈和模型校准。

### 暂不开发

- 摄影社区和内容推荐；
- 商城、会员和商业化；
- 自研完整道路导航；
- 全国全量实时覆盖；
- 端到端大模型直接预测天气。

## 5. 指标体系

### 5.1 北极星指标

`有效拍摄决策数`：用户查看评估并执行或明确取消计划，且事后完成结果反馈的次数。

### 5.2 用户漏斗

```text
打开机会卡 → 查看评估详情 → 查看地点 → 发起路线 → 完成拍摄/取消 → 提交反馈
```

### 5.3 产品指标

- 评估详情点击率；
- 地点选择率；
- 反馈完成率；
- 7 日留存；
- 用户认为“建议有帮助”的比例。

### 5.4 模型指标

- 朝晚霞：Brier Score、AUC、Top-K 命中率、时间窗口 MAE；
- 雷达外推：FSS、CSI、POD、FAR、单体中心位置误差；
- 概率质量：可靠性曲线和分桶命中率；
- 安全引擎：危险区穿越次数必须为 0。

### 5.5 工程指标

- 数据新鲜度和接入成功率；
- API p95 延迟；
- 雷达动画 p95 帧耗时；
- 崩溃率、内存峰值、离线可读率；
- 每项结果的数据血缘完整率。

## 6. 决策与治理规则

1. 官方预警保存原文、来源、发布时间和有效期，禁止模型改写成新的官方结论。
2. AI 内容统一标记“AI 场景评估”或“实验性风险研判”。
3. 雷达、卫星或预报超出新鲜度阈值时，自动降级并停止路线推荐。
4. 安全规则是硬约束，不能因景观高分而放宽。
5. 所有模型必须保留版本号、输入摘要和离线评估结果。
6. 没有超过基线的模型不能进入默认生产路径。

## 7. 里程碑与阶段门

### M0：产品与工程基线

- 总纲、PRD、架构和 Git 规范完成；
- 仓库初始化；
- C++ 核心可构建并通过测试。

### M1：数据可行性

- 一个试点城市；
- 一个历史晚霞案例和一个强对流案例；
- 雷达/卫星/预警适配器接口完成；
- 所有数据可回放。

### M2：首条纵向切片

- Android 显示城市、场景分数和来源；
- 后端返回固定案例；
- Room 支持离线读取；
- 完成一次端到端测试。

### M3：模型基线

- 朝晚霞规则模型；
- 雷达持续性与光流基线；
- 离线评估报告；
- 失败降级策略。

### M4：面试发布

- APK、演示视频、README、架构图；
- 两个完整案例；
- 性能报告与模型卡；
- GitHub Issues、Pull Requests 和版本标签记录完整。

## 8. PM 与程序员的双角色执行方式

每个功能按同一流程推进：

1. PM：写问题、用户故事、价值、范围和验收标准；
2. 数据：确认输入、来源、缺测与许可；
3. 算法：定义基线、指标和失败条件；
4. 开发：Issue → 分支 → 实现 → 测试 → Pull Request；
5. PM验收：按用户路径和指标验收，而不是只看“代码完成”；
6. 复盘：记录偏差、更新路线图和模型卡。
